# Buy / Sell — Design Spec

Date: 2026-09-09  
Status: Draft for user review  
Version: v1 (feature 2)

คิดต้นทุนเมนูเป็นฟีเจอร์ 1 จบแล้ว สเปกนี้เพิ่มเฉพาะระบบซื้อขาย ไม่ย้ายปุ่มซื้อ/ขายไปปนหน้าวัตถุดิบหรือเมนู

## Problem

ราคาซื้อวัตถุดิบแต่ละรอบไม่เท่ากัน ต้องเติมสต็อกและเฉลี่ยต้นทุนต่อหน่วยจากทุกครั้งที่ซื้อ (ไม่สนว่าขายออกไปเท่าไร) และต้องขายเมนูพร้อมเลือกช่องทาง (หัก GP) โดยตัดวัตถุดิบตามสูตร ถ้าของไม่พอต้องขายไม่ได้

## Goals

- หน้าซื้อเข้า: เลือกวัตถุดิบ ปริมาณที่ซื้อ เงินที่จ่าย → เติมคงเหลือ เฉลี่ยต้นทุนต่อหน่วยจากทุกครั้งที่ซื้อ บันทึกประวัติ
- หน้าขายออก: เลือกเมนู จำนวน ช่องทาง → เช็คของ ตัดสต็อก บันทึกยอดหลังหัก GP
- คงเหลือเริ่มต้นเป็น 0 ของวัตถุดิบที่มีอยู่แล้ว ต้องซื้อเข้าก่อนจึงขายเมนูที่ใช้ของนั้นได้
- ของไม่พอ: ไม่บันทึก ไม่ตัดของ บอกว่าขาดอะไรเท่าไร
- ต้นทุนต่อหน่วยหลังซื้อเข้าไปอัปเดตโมดูลคิดต้นทุนอัตโนมัติ
- UI ภาษาไทย สกุลเงินบาท

## Non-goals

- ไม่ยกเลิก/แก้ไขรายการซื้อหรือขายย้อนหลัง
- ไม่มีผู้ขาย, ใบสั่งซื้อ, พิมพ์ฉลาก, รายงานสรรพากร
- ไม่ตัดสต็อกจากหน้าคิดต้นทุน และไม่มีปุ่ม Update Stock ในหน้าวัตถุดิบ
- ไม่มี login

## Relation to costing (feature 1)

หน้าวัตถุดิบ / เมนู / หน่วย / ช่องทางขาย คงเดิม แพ็กตั้งต้น (`purchase_price` / `purchase_quantity`) ไม่ถูกทับตอนซื้อเข้า

ถ้าวัตถุดิบมีประวัติซื้ออย่างน้อย 1 รอบ ต้นทุนต่อหน่วยที่ใช้คิดเมนู = ค่าเฉลี่ยเลขคณิตของต้นทุนต่อหน่วยแต่ละรอบซื้อ ถังน้ำหนักเท่ากันทุกครั้ง ไม่สนคงเหลือและไม่สนว่าขายออกไปเท่าไร

ถ้ายังไม่เคยซื้อเข้า ใช้แพ็กตั้งต้นเหมือนฟีเจอร์คิดต้นทุนเดิม

การขายลดเฉพาะ `remaining_quantity` ไม่เปลี่ยนค่าเฉลี่ยจากประวัติซื้อ

การแก้แพ็กในหน้าคิดต้นทุนด้วยปุ่ม «แก้» ยังทำได้ และมีผลต่อเมนูเฉพาะตอนที่ยังไม่มีประวัติซื้อเข้า การเติมของจริงให้ใช้หน้าซื้อเข้า

## Data model

### `ingredients` (เพิ่มคอลัมน์)

| Column | Type | Rules |
|---|---|---|
| remaining_quantity | numeric | not null, default 0, `>= 0` |

ของเดิมทุกแถวได้ 0

### `stock_purchases`

| Column | Type | Rules |
|---|---|---|
| id | uuid pk | |
| ingredient_id | uuid fk → ingredients.id | restrict on delete |
| quantity | numeric | > 0 |
| amount_paid | numeric | > 0 |
| remaining_after | numeric | >= 0 |
| unit_cost_after | numeric | > 0 |
| created_at | timestamptz | default now() |

ปริมาณใช้หน่วยเดียวกับ `purchase_unit_id` ของวัตถุดิบนั้น ไม่แปลงหน่วย

### `stock_sales`

| Column | Type | Rules |
|---|---|---|
| id | uuid pk | |
| product_id | uuid fk → products.id | restrict on delete |
| sales_channel_id | uuid fk → sales_channels.id | restrict on delete |
| quantity | numeric | > 0 จำนวนจาน/แก้วที่ขาย |
| selling_price_each | numeric | > 0 สำเนาราคา ณ วันขาย |
| fee_percent | numeric | 0–100 สำเนา GP ณ วันขาย |
| product_cost_each | numeric | >= 0 สำเนาต้นทุนต่อจาน ณ วันขาย |
| created_at | timestamptz | default now() |

ไม่เก็บยอดรวมสำเร็จรูป คำนวณตอนอ่านจากค่าที่สำเนาไว้ เพื่อไม่ให้ประวัติเพี้ยนถ้าแก้ราคาเมนูหรือ GP ทีหลัง

### Atomic operations

ซื้อเข้าและขายออกต้องเป็นฟังก์ชัน Postgres (`rpc`) จบใน transaction เดียว ไม่ทำแบบ insert ประวัติแล้วค่อยอัปเดตสต็อกแยกจาก client เพราะถ้าขั้นหลังพลาดจะค้างข้อมูล

RLS ของตารางใหม่เปิดให้ `anon, authenticated` อ่าน/เขียนได้แบบเดียวกับ v1 (ร้านเดียว ยังไม่มี login)

## Calculation

ปัดครึ่งขึ้น 2 ตำแหน่งตอนแสดงผลเท่านั้น รวมภายในก่อนปัด

ต้นทุนต่อหน่วยของรอบซื้อ `i` = `amount_paid_i / quantity_i`

ถ้ามีประวัติซื้อ `n` รอบ (`n >= 1`):

```
average_unit_cost = (u1 + u2 + ... + un) / n
```

แต่ละรอบมีน้ำหนักเท่ากัน แม้ปริมาณที่ซื้อจะไม่เท่ากัน ไม่นำคงเหลือหรือยอดขายมาคิด

ถ้า `n = 0` ใช้แพ็กตั้งต้น: `purchase_price / purchase_quantity`

### ซื้อเข้า

ให้ `qty` = ปริมาณที่ซื้อ, `paid` = เงินที่จ่าย, ทั้งคู่ > 0

```
new_remaining = remaining_quantity + qty
this_unit_cost = paid / qty
average_unit_cost = mean(this_unit_cost และต้นทุนต่อหน่วยของทุก stock_purchases เดิมของวัตถุดิบนี้)
```

บันทึก:

- `remaining_quantity = new_remaining` เท่านั้น ไม่แก้แพ็กตั้งต้น
- แถว `stock_purchases`: quantity, amount_paid, remaining_after, unit_cost_after (= average หลังรอบนี้)

ตัวอย่างที่ล็อกไว้:

- รอบ 1: 100 g 400 บาท → 4.00, คงเหลือ 100, เฉลี่ย 4.00
- รอบ 2: 100 g 450 บาท → 4.50, คงเหลือ 200, เฉลี่ย (4 + 4.5) / 2 = 4.25
- รอบ 3: 50 g 300 บาท → 6.00, คงเหลือ 250, เฉลี่ย (4 + 4.5 + 6) / 3 = 4.833... แสดง 4.83 บาท/g

ขายออกไปกี่กรัมก็ไม่เปลี่ยนค่าเฉลี่ยนี้

### ขายออก

ขายได้เมื่อเมนูมีสูตรอย่างน้อย 1 บรรทัด และมี `selling_price` และเลือกช่องทางแล้ว

ให้ `n` = จำนวนที่ขาย > 0

ต้องใช้ต่อวัตถุดิบ `need = recipe_quantity * n`

ถ้ามีวัตถุดิบใดที่ `remaining_quantity < need` ทั้งรายการล้มเหลว ไม่ตัดของใดเลย ข้อความไทยต่อรายการที่ขาด เช่น `Matcha A ขาดอีก 4 g (มี 2 g ต้องใช้ 6 g)`

ถ้าพอ:

- ลด `remaining_quantity` ของแต่ละวัตถุดิบในสูตรลงตาม `need`
- ไม่แก้แพ็กตั้งต้น และไม่แก้ประวัติซื้อ (ค่าเฉลี่ยต้นทุนไม่เปลี่ยน)
- บันทึก `stock_sales` โดยสำเนา `selling_price_each`, `fee_percent`, `product_cost_each` ณ ตอนนั้น (`product_cost_each` ใช้ต้นทุนเมนูจากค่าเฉลี่ยซื้อถ้ามีประวัติ)

ยอดที่แสดง:

```
gross = selling_price_each * n
channel_fee = gross * (fee_percent / 100)
net_received = gross - channel_fee
net_profit = net_received - (product_cost_each * n)
```

ตัวอย่าง: ขาย 2 แก้ว ราคา 80 GP 12% ต้นทุน 25/แก้ว → ได้เงินจริง 140.80 กำไรสุทธิ 90.80  
ถ้าสูตรใช้ Matcha 3 g ต่อแก้ว ตัด 6 g

## UI

Nav เพิ่มสองลิงก์หลังช่องทางขาย: **ซื้อเข้า** (`/purchases`) และ **ขายออก** (`/sales`)

### ซื้อเข้า

- เลือกวัตถุดิบ โชว์คงเหลือ + ต้นทุนต่อหน่วยเฉลี่ยจากซื้อเข้า (หรือแพ็กตั้งต้นถ้ายังไม่เคยซื้อ) + หน่วย
- ช่องปริมาณที่ซื้อ, เงินที่จ่าย (บาท)
- ตารางประวัติซื้อด้านล่าง (ใหม่สุดบน)

### ขายออก

- เลือกเมนู, จำนวน, ช่องทาง
- สรุปก่อนบันทึก: ของที่จะตัด, ยอดขาย, GP, ได้เงินจริง, กำไรสุทธิ
- ของไม่พอ: ไม่บันทึก โชว์รายการขาด
- เมนูไม่มีสูตรหรือไม่มีราคาขาย: ปุ่มบันทึกใช้ไม่ได้ พร้อมข้อความให้ไปตั้งในระบบคิดต้นทุน
- ตารางประวัติขายด้านล่าง

### วัตถุดิบ (คิดต้นทุน)

คอลัมน์คงเหลือแบบอ่านอย่างเดียว และโชว์ต้นทุนเฉลี่ยจากซื้อเข้าเมื่อมีประวัติ ไม่มีปุ่มเติมสต็อก

## Error handling

| กรณี | พฤติกรรม |
|---|---|
| ปริมาณซื้อ / เงินจ่าย / จำนวนขาย ≤ 0 | ฟอร์มไม่ผ่าน |
| คงเหลือไม่พอ | RPC ล้มเหลว ทั้งรายการไม่บันทึก แสดงของที่ขาด |
| เมนูไม่มีสูตรหรือไม่มีราคาขาย | ขายไม่ได้ |
| ไม่เลือกช่องทาง | ขายไม่ได้ |
| Supabase ล่ม | บันทึกไม่สำเร็จ ไม่แสดงว่าสำเร็จ |
